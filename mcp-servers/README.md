# Campus Assistant — MCP Servers (Week 3)

This directory contains the **Model Context Protocol (MCP)** servers built for Week 3 of the Campus Assistant project. 

These servers expose local university data (documents, timetables, deadlines) as standardized **tools** and **resources** that Large Language Models (LLMs) can securely interact with. Instead of the LLM knowing how to search a database or read a CSV, it just asks the MCP server for information.

---

## Architecture Overview

We implemented **two** MCP servers using the ✨ **FastMCP** (v3) Python library, which provides a significantly cleaner `@mcp.tool` decorator API compared to the raw `mcp` SDK.

### 1. Docs MCP Server (`mcp-servers/docs/server.py`)
Wraps the existing local FAISS vector store generated by the `backend/rag` package.
- **Tools**:
  - `search_docs(query, top_k=5)`: Semantic search over indexed campus documents.
  - `get_chunk(doc_name, page)`: Fetches a specific section of a document.
- **Resources**:
  - `docs://catalog`: Lists all indexed documents and their metadata.

### 2. Timetable MCP Server (`mcp-servers/timetable/server.py`)
Reads the local structured CSV files (`timetable.csv` and `deadlines.csv`) from the `data/timetable/` directory.
- **Tools**:
  - `get_timetable(day, student_group?)`: Fetches the class schedule for a specific day.
  - `get_deadlines(course_id?)`: Fetches upcoming deadlines.
- **Resources**:
  - `timetable://metadata`: Gives an overview of available courses, days, groups, and last-modified timestamps.

## How It Was Built

1. **Dependency installed**: We added `fastmcp` to the existing `backend/.venv`.
2. **Servers created**: Built the two FastMCP servers using the `@mcp.tool` and `@mcp.resource()` decorators.
3. **Backend Client built**: Created `backend/mcp_client.py` using the official `mcp.client.stdio` library.
    - **Crucial detail**: The client uses **stdio transport**. This means when your backend API starts, it *automatically spawns* the MCP servers as background subprocesses by running `python server.py`. They communicate over standard input/output. You do **not** need to manually start the MCP servers on different ports.
4. **Backend Integration**: Updated the `POST /chat` endpoint in `backend/main.py`.
    - Currently (Week 3), the endpoint uses a simple keyword heuristic: if the user asks about "timetables", "deadlines", or days like "Monday", it calls the Timetable MCP tools. Otherwise, it falls back to the RAG document flow.
    - This bridges the gap until **Week 4**, where a LangGraph agent will dynamically decide which tool to call.

## How to Test It

### 1. End-to-End Chat Testing (Integrated API)

Since the backend API automatically spawns the MCP servers, the easiest way to test is through your frontend UI.

1. Ensure your backend is running: `cd backend && .venv\Scripts\python -m uvicorn main:app --host 127.0.0.1 --port 8000 --reload`
2. Open your Campus Assistant Chat UI (http://localhost:3000)
3. Send these exact test queries:
   - **"What is my timetable for Monday?"** *(Tests Timetable MCP Server)*
   - **"What are the deadlines for CS401?"** *(Tests Timetable MCP Server)*
   - **"What is the attendance policy?"** *(Tests Docs flow / RAG)*

### 2. Dedicated Client Testing

You can run the backend client script directly to verify it can connect to both servers, read their capabilities (tools), and execute basic commands.

```bash
# From the backend directory
cd backend
.venv\Scripts\python mcp_client.py
```
**Expected Output:**
```
Testing Docs MCP Server connection...
  -> Connected! Found tools: ['search_docs', 'get_chunk']

Testing Timetable MCP Server connection...
  -> Connected! Found tools: ['get_timetable', 'get_deadlines']
```

### 3. Standalone Server Testing

Both MCP servers have built-in self-tests that bypass MCP entirely and just run the Python functions locally.

```bash
# From the project root, using the backend's virtual environment

# Test Docs Server
backend\.venv\Scripts\python mcp-servers\docs\server.py --test

# Test Timetable Server
backend\.venv\Scripts\python mcp-servers\timetable\server.py --test
```
*Note: If you run these without `--test`, the server will start up in `stdio` mode and appear to hang forever, waiting for MCP protocol messages over stdin.*

## Common Issues & Troubleshooting

- **Unicode/Encoding errors on Windows**: If you modify the servers to print metadata or logs, ensure you use ASCII-safe characters (e.g. `->` instead of `→`). FastMCP uses `utf-8` over stdio, but standard Python `print()` statements on Windows often default to `cp1252`, causing crashes.
- **HuggingFace API Key missing**: The Docs MCP server imports the `rag` package, which requires `HUGGINGFACE_API_KEY` to be set in `backend/.env`. The server automatically handles loading this `.env` file upon startup.
- **FAISS Index Missing**: If the Docs MCP server throws an error in its self-test, you haven't ingested the PDFs yet. Run `python ingest.py` in the `backend/` directory first.
